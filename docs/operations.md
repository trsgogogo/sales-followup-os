# 部署与运维

## 适用范围

单应用进程 + 本地 SQLite + 单团队共享 Token。负责人字段用于分工，不是访问控制。所有持有 Token 的人都能读取客户记录和操作商机。需要多人分权、公网大流量或多租户时，先接入正式身份系统与生产级应用服务器。

固定规则按 UTC 计时；每 30 秒扫描，实际提醒延迟还取决于任务量和外部通知响应。应用重启后会补查到期记录；多个报价档位都错过时只生成最新档位，避免一次发出多轮提醒。

## 发布前检查

1. 使用随机 Token，保存 `.env`；不要把真实客户、数据文件或凭据提交到 Git。
2. 配置 HTTPS 反向代理和请求限流；只将反向代理暴露到公网。
3. 使用非真实客户跑通：新线索 → 联系 → 报价 → 提醒 → 回复 → 取消。
4. 对接实际邮箱 / CRM 回复事件；没有这一步，应用无法知道客户已回复。
5. 配置通知渠道；先验证内部提醒，再决定是否启用 SMTP。
6. 监控 `/healthz` 和工作台失败通知；为应用异常日志配置告警。

## 数据与备份

SQLite 位于 `FOLLOWUP_DB`，默认 `data/followup.db`。不要只复制正在写入的主文件而忽略 WAL。使用 SQLite backup API 创建一致副本：

```bash
python3 -c "import sqlite3; src=sqlite3.connect('data/followup.db'); dst=sqlite3.connect('data/backup.db'); src.backup(dst); dst.close(); src.close()"
```

将备份存到受控位置。恢复时先停止应用，再用备份替换数据库，确认旧连接关闭后再启动。Docker 数据在 `followup-data` 命名卷，可在容器内运行相同备份命令后导出。

## 失败处理

- `pending` 通知：等待下次扫描；重试间隔约 1、2、4、8 分钟，累计 5 次后停止。
- `failed` 通知：修复配置，再手动重试。异常只存类型，避免将带密钥的 Webhook URL 写入数据库。
- `delivery_unknown` 邮件：查服务商已发送记录，不直接重发。发送状态在网络调用前持久化，重启不会盲目重发。
- 客户回复后仍收到内部提醒：核对集成是否写入 `reply`、是否用了正确 lead ID、提醒是否在回复入库之前已投递。已发出的消息无法撤回。
- AI 不可用：自动回退基础模板；不会阻塞定时任务。

出站通知是至少一次投递，外部接收方需要幂等。应用内的任务生成通过事务和唯一索引去重。当前不支持多个应用进程共享同一 SQLite 文件执行扫描与投递。

## 数据保留

此版本保留审计事件，不提供永久删除按钮。正式运营前按团队要求制定数据保留与删除流程；勿将不必要的敏感数据放进客户备注。
